## Gaps Identified (What is Missing)

### GAP-E01: SPEC-E03 Missing Dependency on v11-012

**Location:** `SPEC-E03-gold-layer-dashboard.md` Dependencies section (line 391-403)

**Issue:** The dependencies table shows:
- `gold.events_unified` - Phase E, v11-013
- `gold.events_hourly` - Phase E, v11-013

But does NOT explicitly list:
- `gold.{domain}_threshold_crossings` - Phase E, v11-012

The dashboard queries the threshold crossings table via `gold.events_unified`, but the underlying view `gold.indoor_air_quality_threshold_crossings` is generated by v11-012. This indirect dependency should be documented.

**Impact:** Low - The dependency exists through v11-013, but explicit documentation improves clarity.

**Recommendation:** Add to SPEC-E03 Dependencies table:
```
| gold.{domain}_threshold_crossings | Phase E | v11-012 (via v11-013) |
```

### GAP-E02: Missing `state_field` in SPEC-E02 State Transition Details

**Location:** `SPEC-E02-unified-events-view.md` Section FR-E02-003 (line 62-78)

**Issue:** The state transition details schema shows:
```json
{
  "from_state": "off",
  "to_state": "on",
  "duration_in_previous_ms": 3600000,
  "state_field": "state"   // <-- This field documented
```

However, the table below (line 74-78) does NOT include `state_field` in the field list.

**Impact:** Low - The JSON example shows the field, but the table is incomplete.

### GAP-E03: Inconsistent View Naming Convention

**Location:** Throughout Phase E specs

**Issue:** The specifications use inconsistent naming for the threshold crossings view:

| Document | Name Used |
|----------|-----------|
| SPEC-E01, line 298 | `gold.indoor_air_quality_threshold_crossings` |
| SPEC-E02, line 116-117 | `gold.{domain}_threshold_crossings` |

## Architectural Observations

### 1. View vs Materialized View Decision

SPEC-E01 (FR-E01-009, line 138-142) correctly specifies threshold crossings as a **SQL VIEW** (not materialized):

> "Threshold crossings view is NOT materialized (SQL view):
> - Zero additional storage for crossing events
> - Computed on demand from continuous aggregates
> - Tradeoff: Query cost vs storage cost (Pi optimized for storage)"

This aligns with the Pi resource constraints documented in DECISIONS.md.

### 2. Continuous Aggregate Limitation

SPEC-E02 (line 410-429) proposes `gold.events_hourly` as a continuous aggregate. However, continuous aggregates require a hypertable as the source.

**Question:** `gold.events_unified` is a VIEW, not a hypertable. Can a continuous aggregate be created on a VIEW?

**Answer:** No. TimescaleDB continuous aggregates require a hypertable source.

**Recommendation:** `gold.events_hourly` should be either:
1. A regular materialized view (refreshed manually or via pg_cron)
2. A view that aggregates at query time
3. Built directly from the underlying hypertables (not the unified view)

This needs clarification before implementation. Consider adding this as a **blocker** in STATUS.md.

### 3. Event ID Generation

SPEC-E02 (FR-E02-009, line 159-165) uses `gen_random_uuid()` for event IDs:

> "Event IDs SHALL be:
> - Generated via gen_random_uuid() for V1.1
> - Deterministic replay NOT required for V1.1"

This is appropriate for V1.1 but noted as a potential issue for V1.2 if event deduplication or replay is needed. The documentation correctly defers this decision.

### 4. Dashboard-as-Code Deferral

SPEC-E03 (line 275-293) correctly identifies the dashboard implementation approach:

> **Decision:** Use Option A (JSON export) for V1.1. Consider Option B for V1.2 if dashboards proliferate.

This aligns with the pragmatic approach taken throughout FE-001.

## Summary

Phase E specifications are architecturally sound and well-prepared for implementation. The V1.2 handoff contract is clearly defined. The identified gaps are minor documentation inconsistencies that can be addressed during implementation.

**Key Action Required:** Clarify `gold.events_hourly` implementation approach given continuous aggregate limitations on views.
