## Feature Engineering Patterns

### Pattern: Gold DDL Generation in Rust (not Bash)

- **taskType**: architecture:gold-ddl-generation
- **approach**: Gold layer DDL (continuous aggregates, aligned views, feature tables) is generated by a dedicated Rust CLI tool (`ndp-gold-ddl` / `ndp gold generate`), not Bash string templates. The tool reads stream and domain JSON configs, validates them, and emits idempotent TimescaleDB SQL. Called from `deploy.sh` via `ndp gold sync --stream <id>` or `ndp gold generate --domain <id>`. Output piped to `psql`. Approach chosen because Gold DDL is too complex for Bash (computed expressions, multi-granularity, domain JOINs). Tool lives in `tools/ndp-gold-ddl/` and logic has since been migrated into `crates/ndp-lib/src/gold/`.
- **successRate**: 0.95
- **tags**: gold, ddl, rust, cli, timescaledb, config-driven
- **source**: fe-001 (ADR-FE001-001), ops-001, ops-003
- **status**: current

### Pattern: Config-Driven Continuous Aggregates

- **taskType**: architecture:gold-continuous-aggregates
- **approach**: Each stream's hourly (and daily) TimescaleDB continuous aggregate is fully described in the `gold_etl` section of the stream's JSON config. Fields, metrics (mean/std/min/max/p95), granularities, and refresh policies are all config-declared. The Gold DDL generator reads the config and produces the `CREATE MATERIALIZED VIEW ... WITH (timescaledb.continuous)` plus the `add_continuous_aggregate_policy()` SQL. Adding a new stream to the Gold layer requires only a config change (the "fast-follower test" — no Rust code). Refresh policy: 15-minute schedule, 4-hour lookback window.
- **successRate**: 0.90
- **tags**: gold, continuous-aggregates, config-driven, timescaledb, feature-engineering
- **source**: fe-001 (v11-003, v11-004)
- **status**: current

### Pattern: Cross-Stream Aligned View via FULL OUTER JOIN

- **taskType**: architecture:gold-aligned-view
- **approach**: A single materialized view (`gold.{domain}_aligned_hourly`) joins all streams in a domain on hourly time buckets using FULL OUTER JOINs. This preserves rows even when some streams have no data for a given hour. Column naming convention: `{stream}_{field}_{stat}` (e.g., `indoor_pm25_mean`). The aligned view is the primary input to the intelligence layer and V1.2 pattern detection. Generated from domain config by the Gold DDL tool. NULL handling is the caller's responsibility — FULL OUTER JOINs produce sparse data that the intelligence layer must handle gracefully.
- **successRate**: 0.90
- **tags**: gold, aligned-view, cross-stream, timescaledb, feature-engineering, join
- **source**: fe-001 (v11-005), gold-002 (Section 2)
- **status**: current

### Pattern: Stream Type Classification (observation/state_event/forecast/dimension)

- **taskType**: architecture:stream-classification
- **approach**: Every stream config carries a `stream_type` enum: `observation` (continuous numeric readings, e.g. PM2.5 — role: effect/target), `state_event` (binary/discrete state changes, e.g. window open — role: cause/source), `forecast` (future predictions from external source — role: context), `dimension` (slowly changing reference data — role: metadata). Classification is stored in `data_dictionary.stream_classification` and queryable via MCP. The Gold DDL generator uses stream type to determine appropriate aggregate shapes (state events get transition materializers, not just aggregates).
- **successRate**: 0.85
- **tags**: gold, stream-type, classification, data-dictionary, config-driven
- **source**: fe-001 (v11-001, v11-002)
- **status**: current

### Pattern: Unified Event Abstraction (state_transition + threshold_crossing)

- **taskType**: architecture:unified-events
- **approach**: A `gold.events_unified` view combines two event categories into a consistent schema: `state_transition` events (detected via LAG window function on state_event streams) and `threshold_crossing` events (detected when observation metrics cross objective-declared thresholds). Shared schema: `event_time, stream_id, entity_id, event_type TEXT, details JSONB`. The JSONB payload carries event-type-specific fields (from/to state vs metric/threshold/direction). This view is the primary input for V1.2 pattern detection. Future event types (anomaly, trend_change) follow the same schema.
- **successRate**: 0.85
- **tags**: gold, events, state-transitions, threshold-crossings, unified-schema
- **source**: fe-001 (v11-006, v11-012, v11-013)
- **status**: current

### Pattern: Objectives-Driven Threshold Crossing Detection

- **taskType**: architecture:threshold-crossings
- **approach**: Objectives (declared in domain config: metric, condition, threshold, stream_id) directly drive threshold crossing event generation. The Gold DDL tool reads domain objectives and generates SQL that detects when metrics cross declared thresholds, with LAG-based direction detection (rising/falling). Crossing events reference `objective_id` so downstream consumers know which objective was triggered. Config-driven: adding a new objective (threshold) automatically adds new crossing detection without code changes.
- **successRate**: 0.85
- **tags**: gold, objectives, threshold-crossing, events, config-driven
- **source**: fe-001 (v11-007, v11-012)
- **status**: current

## Intelligence Architecture Patterns

### Pattern: Tiered Intelligence Architecture (NN → SONA → LLM)

- **taskType**: architecture:intelligence-tiers
- **approach**: Three tiers, each handling different failure modes at different costs. **Tier 1 (Online NN)**: Per-domain MLP predicts every Gold refresh cycle (~microseconds), updates weights via online gradient descent with EWC regularization. **Tier 2 (SONA Attention)**: Meta-learner watches NN prediction errors, compares error patterns to ReasoningBank embeddings, applies micro-LoRA for recognized patterns or escalates for novel situations (~milliseconds). **Tier 3 (External LLM via MCP)**: External reasoning for novel situations only — queries APIs, investigates via MCP tools, returns adjustment vector or config change (~seconds, costs per call, rare). Cost scales with rarity. This replaces the v1.2 K-NN-only architecture.
- **successRate**: 0.80
- **tags**: intelligence, online-learning, sona, mcp, tiered, neural-network
- **source**: gold-001 (FEATURE-ROADMAPv1.3.md)
- **status**: current

### Pattern: Feature Engineering Separated from Intelligence (ndp-features crate)

- **taskType**: architecture:crate-boundary-features-vs-intelligence
- **approach**: Runtime feature engineering (EWMA normalization, binary state encoding, text encoding, feature vector assembly) lives in `crates/ndp-features/`, NOT in the intelligence binary. Deploy-time DDL generation (continuous aggregates, views) lives in `crates/ndp-lib/src/gold/`. Intelligence (learning, prediction, SONA, escalation) lives in `crates/ndp-intelligence/`. One binary (`apps/ndp-intelligence-app/`) orchestrates both library crates. The key insight: normalization → encoding → vector assembly is feature engineering (like a CA), not intelligence. Intelligence starts at SEARCH. This boundary enables: CLI to run feature engineering without intelligence, text extraction to iterate independently, and intelligence as a pure consumer of prepared features.
- **successRate**: 0.85
- **tags**: architecture, crate-boundary, ndp-features, ndp-intelligence, feature-engineering
- **source**: gold-001 (FEATURE-ROADMAPv1.3.md, Section "Architecture: Library and Binary Layout")
- **status**: current

### Pattern: EWMA Online Normalization with Persistent State

- **taskType**: architecture:ewma-normalization
- **approach**: Online z-score normalization using Exponential Weighted Moving Average (EWMA): `u(t) = a*x(t) + (1-a)*u(t-1)`, `s2(t) = a*(x(t)-u(t))^2 + (1-a)*s2(t-1)`, `z(t) = (x(t)-u(t))/sqrt(s2(t))`. Alpha (decay factor) is per-field configurable: 0.01 (stable/hourly metrics), 0.05 (default), 0.1 (volatile). Running mean and variance persist in `gold.normalization_state` table (survives restarts). Without persistence, the system re-normalizes from scratch on every restart, producing garbage predictions until warmup completes. This replaces batch z-score which requires seeing all data upfront — incompatible with online learning.
- **successRate**: 0.85
- **tags**: normalization, ewma, online-learning, feature-engineering, persistence
- **source**: gold-001 (FEATURE-ROADMAPv1.3.md, Section "EWMA Normalization")
- **status**: current

### Pattern: Feature Vector Assembly (flat Vec<f32> per timestep)

- **taskType**: architecture:feature-vector-assembly
- **approach**: At each Gold refresh, the feature assembler reads: (1) latest aligned view row (numeric fields), (2) binary state features with derived temporal features (time-since-transition, event-frequency-1h), (3) text encodings (categorical one-hot or reduced MiniLM embeddings). Applies per-field EWMA normalization, concatenates into a flat `Vec<f32>` of fixed domain-specific length, optionally includes lag steps (configurable depth, default 6). Output: `FeatureVector { domain_id, bucket, features: Vec<f32>, feature_names, lag_depth }`. For air quality: ~35 raw features × 7 timesteps = ~245 dimensions. Universal NN input regardless of domain configuration.
- **successRate**: 0.85
- **tags**: feature-engineering, feature-vector, assembly, normalization, encoding
- **source**: gold-001 (FEATURE-ROADMAPv1.3.md, Section "Feature Vector Assembly")
- **status**: current

### Pattern: Online MLP with Elastic Weight Consolidation (EWC)

- **taskType**: architecture:online-mlp-ewc
- **approach**: Simple MLP: `Input → Dense(64) → ReLU → Dense(64) → ReLU → Dense(prediction_targets)`. For air quality: 245→64→64→4. Learns online: predict → wait → observe actual → compute loss → backprop → apply EWC-regularized gradient → update weights. EWC regularization: `total_loss = prediction_loss + lambda * SUM(F_i * (w_i - w_i*)^2)` where F_i is Fisher information for weight i. EWC prevents catastrophic forgetting across seasonal cycles. Consolidation (Fisher snapshot) scheduled weekly. Weight checkpoint to `gold.network_state` hypertable. Warmup: during first 168 steps, K-NN predictions are primary; NN takes over after. K-NN remains as validation baseline.
- **successRate**: 0.80
- **tags**: neural-network, mlp, ewc, online-learning, weight-persistence, intelligence
- **source**: gold-001 (FEATURE-ROADMAPv1.3.md, Section "Online Learning Core")
- **status**: current

### Pattern: K-NN Similarity Search as Bootstrap/Validation Baseline

- **taskType**: architecture:knn-baseline
- **approach**: K-NN similarity search (ruvector-core HNSW + pgvector fallback) is NOT the primary intelligence mechanism in v1.3 — it's the bootstrap (while NN has < warmup steps of training) and validation baseline (compare NN vs K-NN predictions each cycle). Divergence between NN and K-NN predictions is itself a SONA signal. pgvector is the durable storage baseline; ruvector-core HNSW is the acceleration layer (rebuilt from pgvector on startup). HNSW index created per-domain after >100 vectors. The v1.2 architecture used K-NN as primary — v1.3 replaced it with online NN because "K-NN retrieves, it doesn't learn."
- **successRate**: 0.85
- **tags**: knn, similarity-search, ruvector, pgvector, hnsw, baseline, validation
- **source**: gold-001 (FEATURE-ROADMAPv1.3.md), gold-002 (Section 9)
- **status**: current

### Pattern: SONA Meta-Learning with ReasoningBank and Micro-LoRA

- **taskType**: architecture:sona-meta-learning
- **approach**: SONA (Self-Organizing Neural Architecture) watches the NN's prediction errors, not the raw data. Error vector is embedded and compared against ReasoningBank (stored embeddings of known error-pattern/recovery-action pairs). Decision: high similarity to known recovery pattern → apply stored micro-LoRA (fast weight adjustment ~50KB per relationship, EWC++ protected); high similarity to known noise → ignore; low similarity + high error magnitude → escalate to LLM (Tier 3). ReasoningBank capacity is configurable with LRU eviction. SONA runs after the prediction cycle (non-blocking). `ruvector-sona` provides the LoRA + EWC++ implementation.
- **successRate**: 0.75
- **tags**: sona, meta-learning, reasoning-bank, micro-lora, ewc, escalation, intelligence
- **source**: gold-001 (FEATURE-ROADMAPv1.3.md, Section "SONA Integration")
- **status**: experimental

### Pattern: Text Embeddings via ONNX with Model-Agnostic Trait

- **taskType**: architecture:text-embeddings-onnx
- **approach**: Text embedding inference runs in a dedicated `ndp-embedder` container (512MB, separate from ndp-intelligence at 256MB — CPU isolation). TextEmbedder trait is model-agnostic (no ONNX types in interface). OnnxEmbedder implementation uses `ort` crate (Rust ONNX Runtime) with INT8 quantization support. Models stored on Docker volume mount (download-on-first-use if absent). Configuration is per-domain in `domain.json` `embedding` block (model, quantization, dimensions, preprocessing). 33M/384D tier is the quality sweet spot (BGE-small-en-v1.5, snowflake-arctic-embed-s). Passthrough preprocessing for NWS forecasts (transformer models need full sentence context — classical NLP preprocessing hurts quality).
- **successRate**: 0.80
- **tags**: text-embeddings, onnx, miniml, feature-engineering, docker, model-agnostic
- **source**: fe-005
- **status**: current

### Pattern: Composite Embedding (Metric + Text via PCA Reduction)

- **taskType**: architecture:composite-embedding
- **approach**: CompositeEmbedder combines MetricEmbedder output (~32D) + EventEmbedder centroid (PCA-reduced ~16D) into composite vector (~48D). PCA reduction trained on accumulated event embeddings (needs minimum sample size). Composite K-NN search finds past hours where both sensor readings AND forecast context were similar — more specific match than metrics alone. Embedding type is config-driven per stream (`embedding_type: metric|event|composite`). PQ8 quantization optional per stream (>95% recall target vs f32). Tiered retention for event embeddings: hot (24h, all) → warm (30d, anomalous) → cold (forever, centroids only). Metric-only domains are unchanged.
- **successRate**: 0.75
- **tags**: composite-embedding, pca, quantization, retention, text-embeddings, intelligence
- **source**: fe-006
- **status**: experimental

### Pattern: Granger Causality as Warmup Feature Mask (not full pairwise)

- **taskType**: architecture:granger-causality
- **approach**: In v1.3, Granger causality is lightweight: a warmup-period cross-correlation scan that produces a feature mask (which dimensions matter). Used during warmup before NN has enough training data. The NN then learns feature importance through backprop, making full pairwise Granger redundant. In v1.2 (fe-007), full Granger was implemented: similarity-guided candidate selection (top-K K-NN pairs, not O(n²) exhaustive), ADF stationarity test with adaptive preprocessing (raw → first-difference → seasonal-difference), classical F-test or Toda-Yamamoto, BIC lag selection, Benjamini-Hochberg FDR correction. Feature-flagged via `NDP_GRANGER_ENABLED` env var (default false). Results stored in `gold.causal_candidates` table.
- **successRate**: 0.70
- **tags**: granger-causality, statistical-validation, feature-mask, warmup, intelligence
- **source**: fe-007, gold-001 (FEATURE-ROADMAPv1.3.md Decision 29)
- **status**: current (v1.2 full; v1.3 lightweight only)

### Pattern: PG NOTIFY-Driven Intelligence Cycle with Timer Fallback

- **taskType**: architecture:intelligence-cycle-trigger
- **approach**: Intelligence daemon wakes on `LISTEN gold_refresh` PG NOTIFY sent by TimescaleDB after continuous aggregate refresh completes. If no notification within 20 minutes, timer fallback triggers a cycle (handles missed notifications). Cycle: WAKE → OBSERVE (read unprocessed aligned view rows) → EMBED/NORMALIZE → STORE (pgvector) → SEARCH (K-NN) → PREDICT → EVALUATE (past predictions whose horizon elapsed) → SLEEP. Database connection lost → retry with exponential backoff (1s, 2s, 4s, max 60s). Full cycle target: <500ms. Intelligence binary NEVER crashes the ingestion pipeline — errors are logged and retried.
- **successRate**: 0.90
- **tags**: intelligence, pg-notify, cycle, daemon, resilience, timescaledb
- **source**: gold-002 (Section 5), fe-004
- **status**: current

## Operations / Tooling Patterns

### Pattern: Library-First CLI (ndp-lib as single action library)

- **taskType**: architecture:ndp-lib-library-first
- **approach**: All operational logic lives in `crates/ndp-lib/`. The `ndp` CLI (`tools/ndp-cli/`) and any future MCP server are thin wrappers. Functions in ndp-lib take parsed structs (not file paths or URLs) and `&impl DbClient` — enables unit testing without a running database, and config sources (files today, etcd later) without touching ndp-lib. Gold generators, config validators, dictionary sync, dimension sync, domain sync all live in ndp-lib modules. ndp-gold-ddl and ndp-validate standalone binaries became thin wrappers (re-export from ndp-lib) in ops-003. Clean dependency graph: `ndp-types → ndp-lib → ndp-cli (binary)`.
- **successRate**: 0.90
- **tags**: ndp-lib, library-first, cli, architecture, ops
- **source**: ops-001, ops-003
- **status**: current

### Pattern: ndp CLI Entity/Verb Structure

- **taskType**: architecture:ndp-cli-entity-verb
- **approach**: `ndp <entity> <verb> [args]` command structure. Entities: `dictionary`, `dimension`, `stream`, `domain`, `gold`, `validate`, `job`, `pattern`, `event`, `config`, `migration`. Standard verbs with defined semantics: `sync` (idempotent upsert), `list` (read-only), `status` (health), `validate` (no side effects), `diff` (dry-run), `generate` (produce SQL), `apply` (execute SQL), `create`, `push/pull`. All mutating operations return a `SyncReport` struct (processed/created/updated/deleted counts + errors + duration). CLI formats for humans; future MCP server returns JSON. Error handling via `thiserror`-based `NdpLibError` enum.
- **successRate**: 0.90
- **tags**: ndp-cli, entity-verb, commands, ops, structured-output
- **source**: ops-001 (Section "Proposed Command Map"), ops-003
- **status**: current

### Pattern: Deploy.sh Bash-to-Rust Migration with Fallback Pattern

- **taskType**: architecture:deploy-sh-rust-migration
- **approach**: Bash functions in `deploy.sh` are replaced with `ndp` CLI calls using a 4-way binary resolution: `command -v ndp`, `/opt/ndp/bin/ndp`, `target/release/ndp`, `target/debug/ndp`. In ops-001/002, a Bash fallback was retained (`if command -v ndp; then ... else _legacy_bash_impl; fi`). In ops-003, fallbacks were removed — if `ndp` is missing, `error + return 1` (fail loudly, not silently). Parameterized SQL replaces Bash string concatenation (prevents SQL injection). All ops run in `DEPLOY_ENV`-aware mode (integration vs pi) via `--env` flag or environment variable.
- **successRate**: 0.85
- **tags**: deploy-sh, ops, rust-migration, fallback, parameterized-sql
- **source**: ops-001 (D4), ops-002, ops-003
- **status**: current

### Pattern: Two-Layer Config Validation (JSON Schema + Semantic)

- **taskType**: architecture:two-layer-config-validation
- **approach**: All NDP configs use two validation layers: **Layer 1 (JSON Schema)**: Structural validation using JSON Schema draft-07. Validates field presence, types, enums, array items. Produces JSONPath error locations (`$.streams[0].stream_id`). **Layer 2 (Semantic)**: Rust code validates cross-field consistency (e.g., DQ rule references a field that exists, granularity syntax is valid). Layer 2 only runs after Layer 1 passes. Applied to stream configs AND domain configs (fe-002 completed domain config validation gap). All configs must be FLAT format (no wrapper objects) — consistent with stream configs. `ndp validate --stream/--domain/--all` runs both layers.
- **successRate**: 0.90
- **tags**: validation, json-schema, semantic-validation, two-layer, config-driven
- **source**: fe-002, ops-003 (validate module migration)
- **status**: current

### Pattern: Database Bootstrap Two-Layer Architecture

- **taskType**: architecture:database-bootstrap
- **approach**: Database bootstrap is two strictly separated layers. **Layer 0 (Init-scripts, first boot only)**: `deploy/pi/init-scripts/NNN-description.sql` — creates extensions (timescaledb, vector/pgvector), schemas (data_dictionary, silver, gold), roles (ndp_app, grafana_reader), data_dictionary tables, silver utility functions. Uses `NNN-` naming (three-digit zero-padded, hyphen separator) for correct C-locale sort order. Does NOT create Silver hypertables, Gold CAs, or intelligence tables. **Layer 1 (deploy.sh apply, every deploy)**: Config-driven creation of all Silver tables, Gold CAs, aligned views, intelligence objects, dimension data, dictionary sync. Idempotent.
- **successRate**: 0.85
- **tags**: database-bootstrap, init-scripts, deploy-sh, idempotent, architecture
- **source**: ops-008
- **status**: current

### Pattern: Integration Testbed Framework with Manifest-Per-Testbed

- **taskType**: architecture:integration-testbed
- **approach**: Integration testbed framework in `tests/integration/`. Entry point: `run-testbed.sh <type>`. Testbed types: smoke (1 stream, 10 messages, <2 min), regression (all layers, accumulates feature validations), stress (high volume, RSS bounds). Each testbed: `manifest.json` + `compose-override.yml` (env tuning) + `validate.sh`. Features add their own testbed at `product/features/{id}/testbed/`. `deploy.sh apply` is the universal deploy verb for both production and integration — no separate test deploy mechanism. Clean slate = volume prune + container restart (guaranteed, not fastest). MQTT injection via `mosquitto_pub` shell loop. Assertions: `assert_silver_rows`, `assert_bronze_wal_exists`, `assert_etcd_key`.
- **successRate**: 0.80
- **tags**: integration-testing, testbed, smoke, regression, stress, deploy-sh
- **source**: ops-007
- **status**: current

### Pattern: Validation Pipeline with Trust Infrastructure (AgentDB-backed)

- **taskType**: architecture:validation-trust-pipeline
- **approach**: Two phase-specific validation skills: `/validate-plan` (after planning swarm — checks IMPLEMENTATION-BRIEF.md, ACCEPTANCE-MAP.md, LAUNCH-PROMPT.md exist and are internally consistent) and `/validate-impl` (4-tier: Tier 1 cargo build/test/clippy; Tier 2 process adherence: banned deps, anti-stub, file scope, stale refs; Tier 3 spec compliance: AC coverage, test count delta; Tier 4 risk classification: LOW/MEDIUM/HIGH). - **source**: ops-006
- **status**: current

### Pattern: Config-Driven Lifecycle (Adding Stream/Domain via Config Only)

- **taskType**: architecture:config-driven-lifecycle
- **approach**: The platform principle: **config drives behavior, not data lifecycle**. Adding config starts processing. Removing config stops processing. Neither creates nor destroys data. Data deletion requires explicit, intentional action. The "fast-follower test" (fe-001): adding a new stream to the Gold layer via config change only, zero Rust code changes. Every Gold DDL operation is idempotent (CREATE IF NOT EXISTS, upsert). Schema evolution is additive-only (new columns, not dropped columns). Config removal = stop writing, not delete data. Data recovery (`ndp gold recreate --stream/--domain`) is always possible since Gold is 100% derived from Silver. Silver is 100% derived from Bronze. Bronze is append-only.
- **successRate**: 0.90
- **tags**: config-driven, lifecycle, idempotent, additive-schema, fast-follower
- **source**: fe-001 (v11-V01), ops-005
- **status**: current

## Key Architecture Decisions (Decision Log)

From gold-001 FEATURE-ROADMAPv1.3.md:

- **Decision 20**: Online learning replaces K-NN as primary intelligence. K-NN retrieves; it doesn't learn. Stays as bootstrap + baseline.
- **Decision 21**: EWMA normalization, not batch z-score. Online learning requires normalization that adapts without seeing all data upfront.
- **Decision 22**: Feature engineering gets its own crate (`ndp-features`). Deploy-time DDL and runtime feature engineering are different execution models.
- **Decision 23**: One binary, two library crates. Feature engineering and intelligence are temporally coupled (features → learning every cycle). Library boundary enables future split.
- **Decision 24**: EWC from day one. Catastrophic forgetting is the #1 risk in continuous learning.
- **Decision 25**: Tiered architecture NN → SONA → LLM. Each tier handles different failure modes at different costs.
- **Decision 26**: Prediction error as primary anomaly signal. NN's mistakes ARE the anomaly detector.
- **Decision 27**: MCP for external investigation. When local intelligence is stuck, leverage external reasoning.
- **Decision 28**: Normalization state persists in Gold. Same durability guarantees as other Gold data.
- **Decision 29**: Lightweight Granger replaces full pairwise. NN learns feature importance through backprop; full Granger is redundant.
- **Decision 30**: Start with nalgebra MLP, not SONA, for Tier 1. Prove prediction loop works before adding sophistication.

## Deprecated Approaches (DO NOT USE)

- **DuckDB**: Eliminated entirely. Use TimescaleDB.
- **Polars with streaming**: Eliminated. Use TimescaleDB continuous aggregates.
- **K-NN as primary intelligence**: Demoted to bootstrap/baseline in v1.3. Use Online NN.
- **Batch z-score normalization**: Replaced by EWMA online normalization for the intelligence layer.
- **Hardcoded Silver/Gold table names in generators**: All references must come from config (ops-002 pattern).
- **Bash SQL string concatenation in deploy.sh**: Replaced by parameterized Rust SQL in ndp-lib.
- **Mixed init-script naming conventions (NN- vs NNN_)**: Use `NNN-description.sql` three-digit zero-padded with hyphens only.
